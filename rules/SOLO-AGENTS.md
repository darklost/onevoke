# solo-mode 全局工作流规则

## 适用范围与优先级

- 本文件提供跨项目默认规则, 安装后位于 `~/.agents/SOLO-AGENTS.md`. 它不是用户自己的 `~/.agents/AGENTS.md`, 不得互相覆盖.
- 指令优先级从高到低: 当前任务的明确用户指令, 离目标文件最近的项目级 `AGENTS.md` 或 `CLAUDE.md`, 本文件.
- 同目录的 `AGENTS.md` 与 `CLAUDE.md` 冲突, 且当前用户指令未消除冲突时, 停止受影响的操作并询问用户.
- 「Git 工作流」一节仅适用于 Git 仓库. 非 Git 目录不适用分支, worktree, 审核与集成流程, 直接修改文件.
- 操作全局文件看板时, 遵循 `~/.agents/KANBAN-RULES.md`; 开始前通过 `kanban rules` 读取.

## 交流与格式

- 对话, 文档, 代码注释和提交消息默认使用中文; 项目规则另有要求时从项目规则.
- 自然语言使用 ASCII 标点, 中文与英文之间留一个空格. 代码符号, API 名称和原始错误文本保持原样.
- 图表和表格只用 ASCII. 宽度不超过 100 个英文字符或约 50 个汉字; 超出时换行, 拆表或改用列表.
- 要求用户从多个选项中选择时, 选项从 `1` 编号, 并写清每项动作和结果; 用户只回复编号即有效.

## 工作原则

### 范围与复用

- 选择最小且可证实的方案. 分析架构, 边界情况和根因, 不用主观口号替代证据.
- 新增功能前, 先检查既有功能和可复用组件是否已满足需求; 优先复用或扩展现有实现, 避免重复代码.
- 匹配周边文件风格, 不重排, 格式化或重构无关代码.
- 不覆盖, 回退或清理用户已有改动. 用户改动阻塞切分, 验证或集成时, 保留现场并报告.

### 架构与边界

- 新增或变更功能时, 尽可能保持既有架构不变, 维护模块边界, 不得引入循环引用或逆向引用. 必须改变架构或模块边界时, 先说明影响并由用户明确决策.
- 模块依赖必须遵循项目声明的方向; 项目未声明时保持单向, 业务模块不得反向依赖基础模块的具体实现. 跨模块通信只经公开 API, DTO 或事件, 不得直接访问对方内部状态, 私有存储或实现细节.
- 新共享抽象须证明至少两处稳定需求; 单点需求不得提前抽象. 不得以方便为由穿透层级, 复制领域逻辑或建立全局可变状态.
- 改动公共接口, 跨模块数据模型或依赖图前, 先评估影响范围, 列出受影响模块和兼容方案. 删除或合并模块前, 确认无调用方, 迁移路径及回滚风险.

### 代码质量

- 代码优先保证正确, 可读和可维护; 性能优化须有测量或明确瓶颈证据, 不得猜测式优化. 函数和类型保持单一职责, 命名表达业务意图, 不用含糊缩写或无意义通用名.
- 在边界处校验输入并处理空值和异常路径; 不得吞掉错误, 静默降级或以默认值掩盖失败. 资源, 并发与取消须有明确所有权和生命周期, 避免泄漏, 竞态, 无界重试或无上限队列.
- 测试覆盖改动直接影响的行为, 失败路径和回归点, 验证契约而非无关实现细节. 沿用项目既有格式化, lint, 错误处理和日志规范, 不得无说明地禁用检查或压低告警.
- 复杂业务判断记录为何如此, 不写逐行复述注释; 临时代码须在当前任务移除或明确隔离. 性能, 日志和错误信息不得泄露凭据, 个人数据或内部敏感信息.

### 规则沉淀

- 项目架构, API 或长期规则稳定后, 写入仓库文档或对应 `AGENTS.md`, 不得只保存在记忆中.

## 记忆管理

- 本节仅在本机安装了 `memsearch` 时适用. 未安装时整节不适用: 不搭建替代记忆系统, 不手写记忆文件, 任务结束照常按「任务完成」一节总结.
- 使用 `memsearch` 作为唯一记忆系统. 会话流水由 hook 自动写入 `.memsearch/memory/*.md`; 不手写记忆文件, 不手动运行 `memsearch index`.
- 任务完成, PR 合并或阶段目标完成时, 确认自动记录包含任务摘要, 关键决策和适用的 commit hash. 记录缺失时只报告用户, 不自行补写.
- 确认记录完整后提示用户: "建议开新会话, 历史已存 memsearch".

## 探索, 编辑与验证

- monorepo 命令按仓库文档和脚本指定的工作目录运行. 子项目命令从对应子项目目录运行; 根级编排命令从仓库根运行.
- 修改后运行能直接证明改动的最小验证. 测试或环境失败时记录实际命令和错误, 不得标为通过; 既有环境故障同样处理. 错误含敏感值时以 `[REDACTED]` 替换该值, 其余文本保持原样.

## 用户维护文件

- 项目规则声明为用户手动维护的文件, agent 不得修改其内容. 处理已有改动须遵循项目规则; 未声明时, 保留现场, 不得复制, 移动或混入任务提交.
- 在 Git 仓库开始任务时检查当前工作树; 创建任务 worktree 前还须检查主树.

## Git 工作流

### 分支与 worktree

- 默认集成分支由项目规则指定; 项目未指定时, 使用 `refs/remotes/origin/HEAD` 指向的分支. 两者都不存在且无法从本地仓库唯一确定时, 先询问用户.
- 除下述 Markdown 直改路径外, 所有文件修改任务都使用独立任务分支和 `<仓库根目录>/worktrees/<task-name>/` 专用 worktree. `<task-name>` 与分支名相同, 使用简短 kebab-case; 任务分支不得是默认集成分支或 detached `HEAD`. 已处于当前任务的专用 worktree 和任务分支时直接复用.
- 存在 `origin` 且用户未要求仅本地集成时, 先 fetch, 再基于最新 `origin/<默认集成分支>` 创建任务分支; fetch 失败时停止创建并报告. 不存在 `origin` 或用户明确要求仅本地集成时, 基于本地默认集成分支创建任务分支, 并报告未同步远端.
- Markdown 直改路径须同时满足: 任务仅修改 Markdown 文件; 当前分支是默认集成分支或用户明确指定的目标分支; 任务开始时工作树无未提交或未跟踪文件. 任一条件不满足时使用专用 worktree.
- Markdown 直改分支存在 upstream, 且用户未要求仅本地集成时, 修改前必须 fetch 并 fast-forward, 确认 `HEAD` 等于 upstream. 本地领先, 分叉或无法同步时, 改用专用 worktree.

### 提交与 push

- 每个已完成并通过对应验证的独立关注点单独提交, 不混入无关改动. 提交 subject 默认使用中文动宾短语, 如 "修复登录竞态"; 项目规则另有格式时从项目规则.
- 专用任务分支有可写 `origin`, 且用户未要求仅本地集成时, 每个关注点提交后普通 push, 首次使用 `git push -u origin <branch>`.
- Markdown 直改路径先完成验证和必要审核, 再普通 push; 此路径不执行「集成与清理」流程.
- 用户要求 push 时, 检查全部未提交和未 push 状态, 但只提交当前任务明确授权的改动及「用户维护文件」所述 `TODOs.md` 改动, 保留并报告其他用户改动.
- 无 `origin` 或用户明确要求仅本地集成时, 保留本地提交, 跳过 push 并报告. 存在 `origin` 但无法访问, 不可写或用户禁止 push, 且用户未要求仅本地集成时, 保留任务分支和 worktree, 报告后停止集成.
- push 因 non-fast-forward 被拒时, 先 fetch 并检查远端改动, 完成 rebase 后重新验证, 审核按「Codex 审核」的 base 规则处理. 专用任务分支随后可使用 `--force-with-lease`; Markdown 直改分支仍使用普通 push; 默认集成分支永不 force-push. 其他拒绝按项目 PR 流程处理, 无适用流程时停止并报告.
- 多人共享分支使用 `--force-with-lease` 前先通知协作者. 不改写已合并, 已发布或正式 tag 锚定的历史.

### Codex 审核

#### 目标与边界

- 审核目标是确认任务计划或用户明确目标已完整, 正确落实, 重点检查流程是否闭环, 逻辑是否存在漏洞, 以及与该目标直接相关的回归; 不得借审核任意扩大任务范围.
- 审核只处理本任务引入, 加剧或掩盖的问题. 改动前已存在且未被本任务加剧或掩盖的问题, 不得要求修复, 不得阻塞审核或集成, 不得提交用户决策; 用户明确要求纳入本轮时除外.
- 审核结果若要求改变超出用户明确目标的业务逻辑, 用户流程或对外契约, 必须向用户说明影响并由用户明确决策; 不得仅据审核结论自行选择或实施该变更.
- 审核返回任何需要用户注意的问题时, 主代理必须逐项详细解释问题内容、触发条件、实际影响与建议处理方式, 并明确标记提出该问题的 Agent 或审核角色; 汇总多个 Agent 的结果时不得丢失来源归属.
- 审核流程中凡需用户决策, 必须先逐项列出待决策问题, 并为每项说明影响与具体修复方法, 再提供编号选项; 不得只给出抽象选项.
- 运行环境问题若影响验证可信度, 交付可用性或用户数据安全, 必须明确告知用户. 除非改动直接引入, 加剧或掩盖该问题, 或用户明确要求处理, 否则只记录为验证事实, 不得单独判为 blocking, high 或 medium 问题, 亦不得据此要求无关修复.

#### 前置条件与执行

- 豁免条件: 任务恰好修改 1 个文件, 且相对审核 base 的新增与删除代码行合计不超过 10 行. 唯一文件是 `*.md` 或 `*.markdown` 时代码行按 0 计; 其他文件的全部新增与删除行均为代码行, 以 `git diff --numstat <base>..<commit>` 为准. 二进制文件或无法得到数字时不得豁免; 用户明确要求审核时不得豁免.
- 审核前, 将审核 base 以来的全部任务改动按关注点提交, 保持 worktree 无未提交或未跟踪文件.
- 审核 base: 专用任务分支为该分支最近一次基于默认集成分支创建或 rebase 时, 所基于的那个集成分支 commit 的完整 SHA; Markdown 直改路径为修改前 `HEAD` 的完整 SHA. 同一 base 下的修复轮次保持 base 不变; rebase 后 base 更新为新的所基于 commit, 是否重新审核按「集成与清理」的一次性门规则执行.
- 标准审核最多三阶段串行执行. 第一阶段只运行 `PM`, 核对实现是否完整达到 task context; 未达到目标时修复并提交, 使用同一 base、新 `HEAD` 从第一阶段重启. 第二阶段只运行 `QA`, 核对功能正确性、回归、测试与代码质量; 经主代理核实认可的 blocking、high、medium finding 必须修复并提交, 再从第一阶段重启. 第三阶段按改动风险选择安全角色, 两个角色均触发时可并行.
- `CSA` 仅在改动涉及不可信输入、认证授权、凭据、加密、网络协议、远程执行、由不可信输入决定的文件写入、安装更新或发布完整性时运行. `Hacker` 仅在新增或实质改变外部攻击面、执行安全专项审核或用户明确要求时运行. 未触发的角色标记 N/A; 两者均未触发时, `QA` 通过即完成审核.
- 第三阶段仅在实际运行的 `CSA` 或 `Hacker` 返回符合角色提示门槛的实质 finding 时交用户决策, 并提供至少 `1. 修复并重审`、`2. 确认结果并通过`、`3. 停止集成` 三项. 用户选择修复时, 修复并提交后从第一阶段重启; 选择通过时, 在交付说明记录接受的风险与理由. 无合格 finding 时第三阶段直接通过, 不提交 speculative、low 或纯 defense-in-depth advisory 供用户决策.
- 每个角色必须调用 `~/.local/bin/codex-review.sh <CWD> <base-commit> <commit> <role> <task-goal|absolute-spec-path> [review-context]`, 不得直接调用 Codex CLI 绕过 wrapper. `CWD` 必须是目标 Git worktree 的绝对路径; 两个 commit 参数必须是完整 SHA; base 必须是 commit 的祖先; `HEAD` 必须等于 commit; worktree 无未提交或未跟踪文件.
- 一次完整审核中实际运行的角色必须使用相同的 `CWD`、base、commit 与 task context; 任一修复改变 commit 后, 该次审核失效并从第一阶段重启. task context 是权威需求契约: 简短任务可直接传单个字符串, 较长任务使用可读的绝对 spec 路径. 各角色的第 6 参数可传 review context.
- 每个实际运行角色的 stdout 单独保存为报告. 报告目录必须位于目标 worktree 外, 使用仅当前用户可访问的临时目录, 不得混入日志、spec 或其他文件. 用户完成第三阶段决策或本轮终止后清理该目录; 需要保留诊断时先向用户说明. wrapper 自身以 `--sandbox read-only` 和 `--ephemeral` 运行 Codex, 并在结束时校验 worktree 未被改动; 不得通过修改其 sandbox、权限或工具参数绕过门禁.

#### task context 与 review context 模板

task context 按以下五段组织, 缺哪段写哪段, 不必凑齐; 「不在本轮范围」必须显式写:

```text
任务目标: <改什么, 为什么改. 用户已明确的决策与方向写在这里>
用户决策: <用户已明确拍板的方向与取舍>
预期成果: <完成后可观察、可验证的状态>
威胁模型: <受保护资产、可信主体与现实攻击者能力; 非安全任务写 N/A>
不在本轮范围: <见下方清单, 逐条写明并附理由>
```

各阶段角色的可选 review context 用于证据和导航, 不得改变 task context:

```text
本轮已含的修复: <前几轮认可 finding 的修复内容; 首轮省略>
审核重点: <(1)(2)(3) 分条, 指向本轮真正有风险的地方>
验证记录: <已跑过的命令与结果, 含未能执行的项及原因>
环境缺口: <影响验证的实际环境问题与替代证据; 没有则省略>
```

**「不在本轮范围」必须显式写**. 具体边界能让各角色的 risk-bounded stop 生效, 避免把已知取舍或既有问题误报为本轮 finding. 常用条目:

- 向后兼容与数据迁移 (项目已放弃兼容时): `项目已放弃全部向后兼容, 不要提兼容性、迁移或 fallback 类问题.`
- 成本与收益不成比例的理论缺陷. 三条同时成立才可排除: 触发需要额外前置条件已被攻破; 实际后果轻微或反而偏安全; 修复要引入的复杂度明显超过收益 (尤其是本轮刚简化掉的那类). 写法须落到这三点: `<具体项> 的触发前提是 <前提>, 后果是 <后果>, 修复需 <成本>; 不属于本轮范围.`
- 非本轮引入的既有问题: `<具体项> 在改动前已存在 (见 <commit>), 属既有行为而非本次引入, 修它等于扩大本任务范围.`
- 用户已保留自决的区域: `<路径> 由用户自行决定, 本轮不动.`
- 用户已明确拍板的方向: `这是用户明确要求的方向, 不要以 <相反主张> 为由反对方向本身; 用户已知悉相关取舍并计划后续处理.`
- 环境导致的验证缺口: `<命令> 因 <原因> 未能执行, 已用 <替代验证> 覆盖; 不必据此判问题.`

**排除项只能排除"范围", 不能排除"严重级别"**. 不得写成"不要报 high"或"只报文档问题"之类; 真实的 blocking / high / medium 必须仍能被报出. 排除理由必须落到事实 (哪个 commit 引入、什么前提才能触发、用户哪句指示), 不得用"不重要"、"以后再说"一类空话.

- 实现由其他 agent 完成时, 在 review context 里说明并点出自己已修掉的问题, 让 reviewer 重点复查同类半改状态.
- 审核结论采纳后, 判断不修的条目必须在 commit message 或交付说明里写明理由, 不得静默丢弃.

#### 结论与故障处置

- 一次有效审核要求 `PM` 确认目标完整、`QA` 无经主代理认可的 blocking、high、medium finding, 且按触发条件实际运行的 `CSA`、`Hacker` 基于同一 commit 返回结论; 安全角色无合格 finding 时直接通过, 有合格 finding 时须由用户完成决策. 因修复而从第一阶段重启最多 10 次.
- wrapper 参数、认证、前置条件或本地环境错误必须先修正. 仅当参数与前置条件均正确的同一角色调用连续 3 次返回 HTTP 5xx 或明确的 service unavailable 错误时, 视为持续 Codex 后端故障.
- 持续后端故障时不降级到其他 reviewer: 保留分支和 worktree, 报告失败角色、实际错误和已完成的阶段, 停止集成, 等待用户决定重试或改期.
- 重启 10 次后 `PM` 或 `QA` 仍未通过, 或第三阶段未获用户决策时, 同样保留分支和 worktree, 报告未解决项并停止集成. 不得绕过 wrapper 直调 Codex CLI.

### 集成与清理

- 项目要求 PR 或发布门禁, 用户要求暂停或不合回, 或 Bug 修复尚未获得用户验证确认时, 不执行直接集成.
- 审核是集成前的一次性门: 进入集成流程前, 基于当时的审核 base 完成验证和审核并通过. 集成流程 (rebase 到最新集成分支, push, ff 同步) 一旦开始, 集成分支前进只重做 rebase 和验证, 沿用已通过的审核结论, 不再审核. 例外: rebase 引入实质代码冲突并由本人手动解决, 或用户明确要求时, 重新审核.
- 远端集成路径: 在任务 worktree 中 fetch, rebase 到最新 `origin/<默认集成分支>`, 将该远端 commit 记为审核 base, 再验证和审核, 通过后进入集成流程. 已 push 的任务分支在审核通过后仅用 `git push --force-with-lease` 更新; lease 失败时停止, 不覆盖远端改动.
- 本地集成路径: 不存在 `origin` 或用户明确要求仅本地集成时, rebase 到本地默认集成分支, 将其当前 commit 记为审核 base, 再验证和审核, 通过后进入集成流程.
- 集成流程内再次检查默认集成分支; 若其已前进, 按一次性门规则重复 rebase 和验证, 未前进时才允许集成.
- 远端直接集成使用非 force 的 `git push origin <最终任务 commit>:refs/heads/<默认集成分支>`. non-fast-forward 时保持主树不变, 返回同步和验证流程; 其他拒绝按项目 PR 流程处理, 无适用流程时停止并报告. push 成功后 fetch, 再在主树默认集成分支执行 `git merge --ff-only origin/<默认集成分支>`.
- 本地直接集成在主树默认集成分支执行 `git merge --ff-only <任务分支>`, 并报告未 push; fast-forward 失败时返回同步和验证流程. 任何路径都不得产生 merge commit.
- 使用 PR 时, 先 push 当前任务分支. PR 必须说明改了什么, 为何修改和如何验证; 可见 UI 变更附截图; 测试或快照变更列出实际命令. 等待 CI 全部通过后, 按仓库策略 squash 或 rebase 合并, 仓库未指定时默认 squash. 仓库未配置 CI 时先询问用户, 不自动合并.
- 仅在远端直接集成成功且主树已同步, PR 已合并且主树已同步, 或本地集成完成后, 才运行 `~/.local/bin/merge-worktree-memory.py --source <worktree-path>`. 未安装 `memsearch` 时该命令是空操作并正常返回, 照常执行, 不跳过也不据此报错.
- `merge-worktree-memory.py` 成功后, 删除对应 worktree, 本地任务分支及仅为该 worktree 创建的临时或预览 tag; 非本地集成还须删除远端任务分支. 脚本失败时保留 worktree 和分支. 不得删除正式发布 tag.

## 安全

- 凭据只能通过环境变量, secret manager 或仓库约定的 gitignored secret 文件注入.
- 不得把真实 token, 凭据, 敏感服务地址或本机状态写入仓库, 日志, 测试 fixture, dry-run 或发布输出. 敏感服务地址和本机状态包括未公开内网地址, 含敏感路径或参数的公开 endpoint, 本机专属路径和机器标识.

## 任务完成

- 每个任务结束时, 用一句话总结任务目标, 完成情况, commit 状态和所在分支; 非 Git 任务明确写 "无提交, 分支不适用".
