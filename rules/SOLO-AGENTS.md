# solo-mode 全局工作流规则

## 适用范围与优先级

- 跨项目默认规则, 装在 `~/.agents/SOLO-AGENTS.md`. 非用户自己的 `~/.agents/AGENTS.md`, 不互相覆盖.
- 优先级高到低: 当前任务明确用户指令 > 离目标文件最近项目级 `AGENTS.md` 或 `CLAUDE.md` > 本文件.
- 同目录 `AGENTS.md` 与 `CLAUDE.md` 冲突且用户指令未消解时, 停止受影响操作, 问用户.
- 「Git 工作流」节只适用 Git 仓库. 非 Git 目录无分支, worktree, 审核, 集成, 直接改文件.
- 操作全局文件看板遵循 `~/.agents/KANBAN-RULES.md`; 开始前 `kanban rules` 读取.

## 交流与格式

- 对话, 文档, 代码注释, 提交消息默认中文; 项目规则另有要求从项目规则.
- 自然语言用 ASCII 标点, 中英之间留一空格. 代码符号, API 名, 原始错误文本原样.
- 图表和表格只用 ASCII. 宽度不超 100 英文字符或约 50 汉字; 超出则换行, 拆表或改列表.
- 让用户选项时, 从 `1` 编号, 每项写清动作和结果; 用户只回编号即有效.

## 工作原则

### 范围与复用

- 选最小且可证实方案. 分析架构, 边界情况, 根因; 不用口号代替证据.
- 新增功能前先查既有功能和可复用组件; 优先复用或扩展现有实现, 避免重复代码.
- 匹配周边文件风格, 不重排, 格式化或重构无关代码.
- 不覆盖, 回退或清理用户已有改动. 用户改动阻塞切分, 验证或集成时, 保留现场并报告.

### 架构与边界

- 新增或改功能尽量保持既有架构, 维护模块边界, 禁循环引用和逆向引用. 必须改架构或模块边界时, 先说明影响, 由用户决策.
- 模块依赖遵循项目声明方向; 未声明则单向, 业务模块不得反向依赖基础模块具体实现. 跨模块通信只经公开 API, DTO 或事件, 禁直接访问对方内部状态, 私有存储或实现细节.
- 新共享抽象须证明至少两处稳定需求; 单点需求不提前抽象. 禁为方便穿透层级, 复制领域逻辑或建全局可变状态.
- 改公共接口, 跨模块数据模型或依赖图前, 先评估影响范围, 列受影响模块和兼容方案. 删或合并模块前, 确认无调用方, 迁移路径, 回滚风险.

### 代码质量

- 代码先保证正确, 可读, 可维护; 性能优化须有测量或明确瓶颈证据, 禁猜测式优化. 函数和类型单一职责, 命名表达业务意图, 不用含糊缩写或无意义通用名.
- 边界处校验输入, 处理空值和异常路径; 禁吞错误, 静默降级或用默认值掩盖失败. 资源, 并发, 取消须有明确所有权和生命周期, 避免泄漏, 竞态, 无界重试, 无上限队列.
- 测试覆盖改动直接影响行为, 失败路径, 回归点, 验证契约而非无关实现细节. 沿用项目既有格式化, lint, 错误处理, 日志规范, 禁无说明地禁用检查或压低告警.
- 复杂业务判断记录为何如此, 不写逐行复述注释; 临时代码须在当前任务移除或明确隔离. 性能, 日志, 错误信息禁泄露凭据, 个人数据, 内部敏感信息.

### 规则沉淀

- 项目架构, API 或长期规则稳定后写入仓库文档或对应 `AGENTS.md`, 禁只存记忆.

## 记忆管理

- 本节只在本机装了 `memsearch` 时适用. 未装则整节不适用: 不搭替代记忆系统, 不手写记忆文件, 任务结束照常按「任务完成」节总结.
- `memsearch` 为唯一记忆系统. 会话流水由 hook 自动写入 `.memsearch/memory/*.md`; 不手写记忆文件, 不手动跑 `memsearch index`.
- 任务完成, PR 合并或阶段目标完成时, 确认自动记录含任务摘要, 关键决策, 适用 commit hash. 记录缺失只报告用户, 不自行补写.
- 确认记录完整后提示用户: "建议开新会话, 历史已存 memsearch".

## 探索, 编辑与验证

- monorepo 命令按仓库文档和脚本指定工作目录运行. 子项目命令从对应子项目目录跑; 根级编排命令从仓库根跑.
- 改后跑能直接证明改动的最小验证. 测试或环境失败时记录实际命令和错误, 禁标为通过; 既有环境故障同样处理. 错误含敏感值时该值换 `[REDACTED]`, 其余文本原样.

## 用户维护文件

- 项目规则声明为用户手动维护的文件, agent 禁改其内容. 处理已有改动遵循项目规则; 未声明则保留现场, 禁复制, 移动或混入任务提交.
- Git 仓库开始任务时检查当前工作树; 建任务 worktree 前还须检查主树.

## Git 工作流

### 分支与 worktree

- 默认集成分支由项目规则指定; 未指定用 `refs/remotes/origin/HEAD` 指向的分支. 两者都无且本地仓库无法唯一确定时先问用户.
- 除下述 Markdown 直改路径外, 所有改文件任务都用独立任务分支和 `<仓库根目录>/worktrees/<task-name>/` 专用 worktree. `<task-name>` 同分支名, 短 kebab-case; 任务分支不得是默认集成分支或 detached `HEAD`. 已在当前任务专用 worktree 和任务分支时直接复用.
- 有 `origin` 且用户未要求仅本地集成时, 先 fetch, 再基于最新 `origin/<默认集成分支>` 建任务分支; fetch 失败则停止创建并报告. 无 `origin` 或用户明确要求仅本地集成时, 基于本地默认集成分支建任务分支, 报告未同步远端.
- Markdown 直改路径须同时满足: 任务只改 Markdown 文件; 当前分支是默认集成分支或用户明确指定目标分支; 任务开始时工作树无未提交或未跟踪文件. 任一不满足用专用 worktree.
- Markdown 直改分支有 upstream 且用户未要求仅本地集成时, 改前必须 fetch 并 fast-forward, 确认 `HEAD` 等于 upstream. 本地领先, 分叉或无法同步时改用专用 worktree.

### 提交与 push

- 每个已完成并通过对应验证的独立关注点单独提交, 不混无关改动. 提交 subject 默认中文动宾短语, 如 "修复登录竞态"; 项目规则另有格式从项目规则.
- 专用任务分支有可写 `origin` 且用户未要求仅本地集成时, 每个关注点提交后普通 push, 首次用 `git push -u origin <branch>`.
- Markdown 直改路径先完成验证和必要审核再普通 push; 此路径不走「集成与清理」流程.
- 用户要求 push 时, 检查全部未提交和未 push 状态, 但只提交当前任务明确授权的改动及「用户维护文件」所述 `TODOs.md` 改动, 保留并报告其他用户改动.
- 无 `origin` 或用户明确要求仅本地集成时, 保留本地提交, 跳过 push 并报告. 有 `origin` 但无法访问, 不可写或用户禁 push, 且用户未要求仅本地集成时, 保留任务分支和 worktree, 报告后停止集成.
- push 因 non-fast-forward 被拒时, 先 fetch 查远端改动, rebase 后重新验证, 审核按「Codex 审核」base 规则处理. 专用任务分支随后可用 `--force-with-lease`; Markdown 直改分支仍普通 push; 默认集成分支永不 force-push. 其他拒绝按项目 PR 流程处理, 无适用流程则停止并报告.
- 多人共享分支用 `--force-with-lease` 前先通知协作者. 不改写已合并, 已发布或正式 tag 锚定的历史.

### Codex 审核

#### 目标与边界

- 审核目标: 确认任务计划或用户明确目标已完整, 正确落实, 重点查流程是否闭环, 逻辑有无漏洞, 及与该目标直接相关的回归; 禁借审核扩大任务范围.
- 审核只处理本任务引入, 加剧或掩盖的问题. 改动前已存在且未被本任务加剧或掩盖的问题, 禁要求修复, 禁阻塞审核或集成, 禁提交用户决策; 用户明确要求纳入本轮除外.
- 审核结果若要求改变超出用户明确目标的业务逻辑, 用户流程或对外契约, 必须向用户说明影响并由用户决策; 禁仅据审核结论自行选择或实施该变更.
- 审核返回任何需用户注意的问题时, 主代理必须逐项详解问题内容、触发条件、实际影响与建议处理方式, 并明确标记提出该问题的 Agent 或审核角色; 汇总多 Agent 结果时不得丢失来源归属.
- 审核流程中凡需用户决策, 必须先逐项列出待决策问题, 每项说明影响与具体修复方法, 再给编号选项; 禁只给抽象选项.
- 运行环境问题若影响验证可信度, 交付可用性或用户数据安全, 必须明确告知用户. 除非改动直接引入, 加剧或掩盖该问题, 或用户明确要求处理, 否则只记为验证事实, 禁单独判为 blocking, high 或 medium 问题, 亦禁据此要求无关修复.

#### 前置条件与执行

- 豁免条件: 任务恰改 1 个文件, 且相对审核 base 的新增与删除代码行合计不超 10 行. 唯一文件是 `*.md` 或 `*.markdown` 时代码行按 0 计; 其他文件全部新增与删除行均为代码行, 以 `git diff --numstat <base>..<commit>` 为准. 二进制文件或拿不到数字时不得豁免; 用户明确要求审核时不得豁免.
- 审核前, 把审核 base 以来全部任务改动按关注点提交, 保持 worktree 无未提交或未跟踪文件.
- 审核 base: 专用任务分支为该分支最近一次基于默认集成分支创建或 rebase 时所基于的那个集成分支 commit 的完整 SHA; Markdown 直改路径为改前 `HEAD` 完整 SHA. 同一 base 下修复轮次保持 base 不变; rebase 后 base 更新为新的所基于 commit, 是否重审按「集成与清理」一次性门规则执行.
- 标准审核最多三阶段串行. 第一阶段只跑 `PM`, 核对实现是否完整达到 task context; 未达标则修复并提交, 用同一 base、新 `HEAD` 从第一阶段重启. 第二阶段只跑 `QA`, 核对功能正确性、回归、测试与代码质量; 经主代理核实认可的 blocking、high、medium finding 必须修复并提交, 再从第一阶段重启. 第三阶段按改动风险选安全角色, 两角色均触发时可并行.
- `CSA` 仅在改动涉及不可信输入、认证授权、凭据、加密、网络协议、远程执行、由不可信输入决定的文件写入、安装更新或发布完整性时跑. `Hacker` 仅在新增或实质改变外部攻击面、执行安全专项审核或用户明确要求时跑. 未触发角色标 N/A; 两者均未触发时 `QA` 通过即完成审核.
- 第三阶段仅在实际运行的 `CSA` 或 `Hacker` 返回符合角色提示门槛的实质 finding 时交用户决策, 并提供至少 `1. 修复并重审`、`2. 确认结果并通过`、`3. 停止集成` 三项. 用户选修复则修复提交后从第一阶段重启; 选通过则在交付说明记录接受的风险与理由. 无合格 finding 时第三阶段直接通过, 不提交 speculative、low 或纯 defense-in-depth advisory 供用户决策.
- 每个角色必须调 `~/.local/bin/codex-review.sh <CWD> <base-commit> <commit> <role> <task-goal|absolute-spec-path> [review-context]`, 禁直接调 Codex CLI 绕过 wrapper. `CWD` 必须是目标 Git worktree 绝对路径; 两个 commit 参数必须是完整 SHA; base 必须是 commit 祖先; `HEAD` 必须等于 commit; worktree 无未提交或未跟踪文件.
- 一次完整审核中实际运行的角色必须用相同 `CWD`、base、commit 与 task context; 任一修复改变 commit 后该次审核失效, 从第一阶段重启. task context 是权威需求契约: 短任务可直接传单个字符串, 长任务用可读的绝对 spec 路径. 各角色第 6 参数可传 review context.
- 每个实际运行角色的 stdout 单独存为报告. 报告目录必须在目标 worktree 外, 用仅当前用户可访问的临时目录, 禁混入日志、spec 或其他文件. 用户完成第三阶段决策或本轮终止后清理该目录; 需保留诊断先向用户说明. wrapper 自身以 `--sandbox read-only` 和 `--ephemeral` 跑 Codex, 结束时校验 worktree 未被改动; 禁改其 sandbox、权限或工具参数绕过门禁.

#### task context 与 review context 模板

task context 按以下五段组织, 缺哪段写哪段, 不必凑齐; 「不在本轮范围」必须显式写:

```text
任务目标: <改什么, 为什么改. 用户已明确的决策与方向写在这里>
用户决策: <用户已明确拍板的方向与取舍>
预期成果: <完成后可观察、可验证的状态>
威胁模型: <受保护资产、可信主体与现实攻击者能力; 非安全任务写 N/A>
不在本轮范围: <见下方清单, 逐条写明并附理由>
```

各阶段角色的可选 review context 用于证据和导航, 禁改 task context:

```text
本轮已含的修复: <前几轮认可 finding 的修复内容; 首轮省略>
审核重点: <(1)(2)(3) 分条, 指向本轮真正有风险的地方>
验证记录: <已跑过的命令与结果, 含未能执行的项及原因>
环境缺口: <影响验证的实际环境问题与替代证据; 没有则省略>
```

**「不在本轮范围」必须显式写**. 具体边界让各角色 risk-bounded stop 生效, 避免把已知取舍或既有问题误报为本轮 finding. 常用条目:

- 向后兼容与数据迁移 (项目已放弃兼容时): `项目已放弃全部向后兼容, 不要提兼容性、迁移或 fallback 类问题.`
- 成本与收益不成比例的理论缺陷. 三条同时成立才可排除: 触发需额外前置条件已被攻破; 实际后果轻微或反而偏安全; 修复引入的复杂度明显超收益 (尤其本轮刚简化掉那类). 写法须落到这三点: `<具体项> 的触发前提是 <前提>, 后果是 <后果>, 修复需 <成本>; 不属于本轮范围.`
- 非本轮引入的既有问题: `<具体项> 在改动前已存在 (见 <commit>), 属既有行为而非本次引入, 修它等于扩大本任务范围.`
- 用户已保留自决的区域: `<路径> 由用户自行决定, 本轮不动.`
- 用户已明确拍板的方向: `这是用户明确要求的方向, 不要以 <相反主张> 为由反对方向本身; 用户已知悉相关取舍并计划后续处理.`
- 环境导致的验证缺口: `<命令> 因 <原因> 未能执行, 已用 <替代验证> 覆盖; 不必据此判问题.`

**排除项只能排除"范围", 不能排除"严重级别"**. 禁写成"不要报 high"或"只报文档问题"; 真实 blocking / high / medium 必须仍能报出. 排除理由必须落到事实 (哪个 commit 引入、什么前提才触发、用户哪句指示), 禁用"不重要"、"以后再说"一类空话.

- 实现由其他 agent 完成时, 在 review context 说明并点出自己已修掉的问题, 让 reviewer 重点复查同类半改状态.
- 审核结论采纳后, 判断不修的条目必须在 commit message 或交付说明写明理由, 禁静默丢弃.

#### 结论与故障处置

- 一次有效审核要求 `PM` 确认目标完整、`QA` 无经主代理认可的 blocking、high、medium finding, 且按触发条件实际运行的 `CSA`、`Hacker` 基于同一 commit 返回结论; 安全角色无合格 finding 直接通过, 有合格 finding 须由用户完成决策. 因修复从第一阶段重启最多 10 次.
- wrapper 参数、认证、前置条件或本地环境错误必须先修正. 仅当参数与前置条件均正确的同一角色调用连续 3 次返回 HTTP 5xx 或明确 service unavailable 错误时, 视为持续 Codex 后端故障.
- 持续后端故障时不降级到其他 reviewer: 保留分支和 worktree, 报告失败角色、实际错误和已完成阶段, 停止集成, 等用户决定重试或改期.
- 重启 10 次后 `PM` 或 `QA` 仍未通过, 或第三阶段未获用户决策时, 同样保留分支和 worktree, 报告未解决项并停止集成. 禁绕过 wrapper 直调 Codex CLI.

### 集成与清理

- 项目要求 PR 或发布门禁, 用户要求暂停或不合回, 或 Bug 修复未获用户验证确认时, 不做直接集成.
- 审核是集成前一次性门: 进集成流程前, 基于当时审核 base 完成验证和审核并通过. 集成流程 (rebase 到最新集成分支, push, ff 同步) 一旦开始, 集成分支前进只重做 rebase 和验证, 沿用已通过审核结论, 不再审核. 例外: rebase 引入实质代码冲突并由本人手动解决, 或用户明确要求时重审.
- 远端集成路径: 在任务 worktree fetch, rebase 到最新 `origin/<默认集成分支>`, 该远端 commit 记为审核 base, 再验证和审核, 通过后进集成流程. 已 push 的任务分支审核通过后仅用 `git push --force-with-lease` 更新; lease 失败则停止, 不覆盖远端改动.
- 本地集成路径: 无 `origin` 或用户明确要求仅本地集成时, rebase 到本地默认集成分支, 其当前 commit 记为审核 base, 再验证和审核, 通过后进集成流程.
- 集成流程内再查默认集成分支; 若已前进, 按一次性门规则重复 rebase 和验证, 未前进才允许集成.
- 远端直接集成用非 force 的 `git push origin <最终任务 commit>:refs/heads/<默认集成分支>`. non-fast-forward 时保持主树不变, 回同步和验证流程; 其他拒绝按项目 PR 流程处理, 无适用流程则停止并报告. push 成功后 fetch, 再在主树默认集成分支跑 `git merge --ff-only origin/<默认集成分支>`.
- 本地直接集成在主树默认集成分支跑 `git merge --ff-only <任务分支>`, 并报告未 push; fast-forward 失败回同步和验证流程. 任何路径都不得产生 merge commit.
- 用 PR 时先 push 当前任务分支. PR 必须说明改了什么, 为何改, 如何验证; 可见 UI 变更附截图; 测试或快照变更列实际命令. 等 CI 全通过后, 按仓库策略 squash 或 rebase 合并, 仓库未指定默认 squash. 仓库未配 CI 先问用户, 不自动合并.
- 仅在远端直接集成成功且主树已同步, PR 已合并且主树已同步, 或本地集成完成后, 才跑 `~/.local/bin/merge-worktree-memory.py --source <worktree-path>`. 未装 `memsearch` 时该命令是空操作并正常返回, 照常执行, 不跳过也不据此报错.
- `merge-worktree-memory.py` 成功后, 删对应 worktree, 本地任务分支及仅为该 worktree 建的临时或预览 tag; 非本地集成还须删远端任务分支. 脚本失败则保留 worktree 和分支. 禁删正式发布 tag.

## 安全

- 凭据只能经环境变量, secret manager 或仓库约定的 gitignored secret 文件注入.
- 禁把真实 token, 凭据, 敏感服务地址或本机状态写入仓库, 日志, 测试 fixture, dry-run 或发布输出. 敏感服务地址和本机状态含未公开内网地址, 含敏感路径或参数的公开 endpoint, 本机专属路径, 机器标识.

## 任务完成

- 每个任务结束时, 一句话总结任务目标, 完成情况, commit 状态和所在分支; 非 Git 任务明确写 "无提交, 分支不适用".
