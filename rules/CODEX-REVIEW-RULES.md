# Codex 审核规则

本文件是 `~/.agents/SOLO-AGENTS.md`「Git 工作流」的审核环节契约, 装在 `~/.agents/CODEX-REVIEW-RULES.md`. 优先级与 `SOLO-AGENTS.md` 同级: 当前任务明确用户指令 > 项目级 `AGENTS.md` 或 `CLAUDE.md` > 本文件.

## 目标与边界

- 审核目标: 确认任务计划或用户明确目标已完整, 正确落实, 重点查流程是否闭环, 逻辑有无漏洞, 及与该目标直接相关的回归; 禁借审核扩大任务范围.
- 审核只处理本任务引入, 加剧或掩盖的问题. 改动前已存在且未被本任务加剧或掩盖的问题, 禁要求修复, 禁阻塞审核或集成, 禁提交用户决策; 用户明确要求纳入本轮除外.
- 审核结果若要求改变超出用户明确目标的业务逻辑, 用户流程或对外契约, 必须向用户说明影响并由用户决策; 禁仅据审核结论自行选择或实施该变更.
- 审核返回任何需用户注意的问题时, 主代理必须逐项详解问题内容、触发条件、实际影响与建议处理方式, 并明确标记提出该问题的 Agent 或审核角色; 汇总多 Agent 结果时不得丢失来源归属.
- 审核流程中凡需用户决策, 必须先逐项列出待决策问题, 每项说明影响与具体修复方法, 再给编号选项; 禁只给抽象选项.
- 运行环境问题若影响验证可信度, 交付可用性或用户数据安全, 必须明确告知用户. 除非改动直接引入, 加剧或掩盖该问题, 或用户明确要求处理, 否则只记为验证事实, 禁单独判为 blocking, high 或 medium 问题, 亦禁据此要求无关修复.

## 前置条件与执行

- 豁免条件: 任务恰改 1 个文件, 且相对审核 base 的新增与删除代码行合计不超 10 行. 唯一文件是 `*.md` 或 `*.markdown` 时代码行按 0 计; 其他文件全部新增与删除行均为代码行, 以 `git diff --numstat <base>..<commit>` 为准. 二进制文件或拿不到数字时不得豁免; 用户明确要求审核时不得豁免.
- 走豁免路径必须在集成前明确告知用户"本次未走审核闭环", 并写出触发的豁免条件 (改了哪个文件, 新增与删除行数). 禁静默跳过. 用户随后要求审核时照常执行完整流程.
- 审核前, 把审核 base 以来全部任务改动按关注点提交, 保持 worktree 无未提交或未跟踪文件.
- 审核 base: 专用任务分支为该分支最近一次基于默认集成分支创建或 rebase 时所基于的那个集成分支 commit 的完整 SHA; Markdown 直改路径为改前 `HEAD` 完整 SHA. 同一 base 下修复轮次保持 base 不变; rebase 后 base 更新为新的所基于 commit, 是否重审按「集成与清理」一次性门规则执行.
- 标准审核最多三阶段串行. 第一阶段只跑 `PM`, 核对实现是否完整达到 task context; PM finding 与 QA 同样按 blocking、high、medium、low 分级, 只有经主代理核实认可的 blocking、high、medium 才必须修复并提交, 用同一 base、新 `HEAD` 从第一阶段重启; low 与建议类不阻塞, 按「审核结论采纳后」规则写明不修理由. 第二阶段只跑 `QA`, 核对功能正确性、回归、测试与代码质量; 经主代理核实认可的 blocking、high、medium finding 必须修复并提交, 修复后从第二阶段重启, 沿用同一 base 下已通过的 `PM` 结论, 不重跑 `PM`. 第三阶段按改动风险选安全角色, 两角色均触发时可并行.
- `CSA` 仅在改动涉及不可信输入、认证授权、凭据、加密、网络协议、远程执行、由不可信输入决定的文件写入、安装更新或发布完整性时跑. `Hacker` 仅在新增或实质改变外部攻击面、执行安全专项审核或用户明确要求时跑. 未触发角色标 N/A; 两者均未触发时 `QA` 通过即完成审核.
- 第三阶段仅在实际运行的 `CSA` 或 `Hacker` 返回符合角色提示门槛的实质 finding 时交用户决策, 并提供至少 `1. 修复并重审`、`2. 确认结果并通过`、`3. 停止集成` 三项. 用户选修复则修复提交后从第二阶段重启 (同 `QA` 修复, 不重跑 `PM`); 选通过则在交付说明记录接受的风险与理由. 无合格 finding 时第三阶段直接通过, 不提交 speculative、low 或纯 defense-in-depth advisory 供用户决策.
- 每个角色必须调 `~/.local/bin/codex-review.sh <CWD> <base-commit> <commit> <role> <task-goal|absolute-spec-path> [review-context]`, 禁直接调 Codex CLI 绕过 wrapper. `CWD` 必须是目标 Git worktree 绝对路径; 两个 commit 参数必须是完整 SHA; base 必须是 commit 祖先; `HEAD` 必须等于 commit; worktree 无未提交或未跟踪文件.
- 一次完整审核中实际运行的角色必须用相同 `CWD`、base 与 task context; `QA`、`CSA`、`Hacker` 还必须基于同一 commit, 任一修复改变 commit 后这三个角色的结论一并失效, 从第二阶段重启. `PM` 是唯一例外: 同一 base 下 `PM` 通过后, 后续所有修复轮次沿用该结论, 允许 `PM` 的 commit 早于其余角色. base 改变则全部结论失效, 从第一阶段重启. task context 是权威需求契约: 短任务可直接传单个字符串, 长任务用可读的绝对 spec 路径. 各角色第 6 参数可传 review context.
- 每个实际运行角色的 stdout 单独存为报告. 报告目录必须在目标 worktree 外, 用仅当前用户可访问的临时目录, 禁混入日志、spec 或其他文件. 用户完成第三阶段决策或本轮终止后清理该目录; 需保留诊断先向用户说明. wrapper 自身以 `--sandbox read-only` 和 `--ephemeral` 跑 Codex, 结束时校验 worktree 未被改动; 禁改其 sandbox、权限或工具参数绕过门禁.

## task context 与 review context 模板

task context 按以下五段组织, 缺哪段写哪段, 不必凑齐; 「不在本轮范围」必须显式写:

```text
任务目标: <改什么, 为什么改. 用户已明确的决策与方向写在这里>
用户决策: <用户已明确拍板的方向与取舍>
预期成果: <完成后可观察、可验证的状态>
威胁模型: <受保护资产、可信主体与现实攻击者能力; 非安全任务写 N/A>
不在本轮范围: <见下方清单, 逐条写明并附理由>
```

各阶段角色的可选 review context 用于证据和导航, 禁改 task context:

```text
本轮已含的修复: <前几轮认可 finding 的修复内容; 首轮省略>
审核重点: <(1)(2)(3) 分条, 指向本轮真正有风险的地方>
验证记录: <已跑过的命令与结果, 含未能执行的项及原因>
环境缺口: <影响验证的实际环境问题与替代证据; 没有则省略>
```

**「不在本轮范围」必须显式写**. 具体边界让各角色 risk-bounded stop 生效, 避免把已知取舍或既有问题误报为本轮 finding. 常用条目:

- 向后兼容与数据迁移 (项目已放弃兼容时): `项目已放弃全部向后兼容, 不要提兼容性、迁移或 fallback 类问题.`
- 成本与收益不成比例的理论缺陷. 三条同时成立才可排除: 触发需额外前置条件已被攻破; 实际后果轻微或反而偏安全; 修复引入的复杂度明显超收益 (尤其本轮刚简化掉那类). 写法须落到这三点: `<具体项> 的触发前提是 <前提>, 后果是 <后果>, 修复需 <成本>; 不属于本轮范围.`
- 非本轮引入的既有问题: `<具体项> 在改动前已存在 (见 <commit>), 属既有行为而非本次引入, 修它等于扩大本任务范围.`
- 用户已保留自决的区域: `<路径> 由用户自行决定, 本轮不动.`
- 用户已明确拍板的方向: `这是用户明确要求的方向, 不要以 <相反主张> 为由反对方向本身; 用户已知悉相关取舍并计划后续处理.`
- 环境导致的验证缺口: `<命令> 因 <原因> 未能执行, 已用 <替代验证> 覆盖; 不必据此判问题.`

**排除项只能排除"范围", 不能排除"严重级别"**. 禁写成"不要报 high"或"只报文档问题"; 真实 blocking / high / medium 必须仍能报出. 排除理由必须落到事实 (哪个 commit 引入、什么前提才触发、用户哪句指示), 禁用"不重要"、"以后再说"一类空话.

- 实现由其他 agent 完成时, 在 review context 说明并点出自己已修掉的问题, 让 reviewer 重点复查同类半改状态.
- 审核结论采纳后, 判断不修的条目必须在 commit message 或交付说明写明理由, 禁静默丢弃.

## 结论与故障处置

- 一次有效审核要求 `PM` 与 `QA` 均无经主代理认可的 blocking、high、medium finding, 且按触发条件实际运行的 `CSA`、`Hacker` 基于同一 commit 返回结论; 安全角色无合格 finding 直接通过, 有合格 finding 须由用户完成决策.
- 重启轮次不设次数上限. 但同一 finding 连续多轮修复仍未通过时, 停止自转, 向用户说明卡在哪、已试过什么、下一步选项, 由用户决策.
- wrapper 参数、认证、前置条件或本地环境错误必须先修正. 仅当参数与前置条件均正确的同一角色调用连续 3 次返回 HTTP 5xx 或明确 service unavailable 错误时, 视为持续 Codex 后端故障.
- `PM` 或 `QA` 持续后端故障时不降级到其他 reviewer: 保留分支和 worktree, 报告失败角色、实际错误和已完成阶段, 停止集成, 等用户决定重试或改期.
- `CSA` 或 `Hacker` 持续后端故障不阻塞审核: 该角色记为"因后端故障未完成", 在交付说明和给用户的汇报里写明, 审核结论由 `PM` 与 `QA` 决定. 两个安全角色都触发时其中一个故障, 另一个照常出结论并按第三阶段规则处理.
- 第三阶段未获用户决策时, 保留分支和 worktree, 报告未解决项并停止集成. 禁绕过 wrapper 直调 Codex CLI.
