# 全局文件看板规则

## 适用范围

- 本文件约束全局 `kanban` 命令管理的所有看板. 用户指令和目标项目规则优先.
- 卡片只保存任务契约和执行记录, 不覆盖项目规则, 安全门禁或用户决策.
- Agent 操作看板前先运行 `kanban rules`, 再读取目标卡片.

## 存储与定位

- `kanban/` 是本机共享数据, 唯一实例位于主 worktree 根目录, 不进 Git. 任务 worktree 不建副本, 镜像或符号链接.
- 看板只供同主机, 同文件系统的 Agent 共享; 远程 Agent 不可见.
- 定位顺序是 `KANBAN_DIR` -> 当前 Git 仓库主 worktree 的 `kanban/` -> 从当前目录向上查找 `kanban/`.
- `KANBAN_DIR` 仅用于测试, 非 Git 项目或明确覆盖. 正常 Git 项目不设置.
- 从任意 worktree 定位看板时使用:

```sh
MAIN_WORKTREE="$(git worktree list --porcelain | sed -n '1s/^worktree //p')"
KANBAN_DIR="$MAIN_WORKTREE/kanban"
```

- 看板操作本身不建分支, 不提交, 不 push, 不审核. 卡片对应的代码任务仍按项目规则执行.
- 禁止提交 `kanban/`, 禁止修改项目 `.gitignore` 传播本机看板.

## 命令契约

`kanban` 是创建入口, 查询和迁移状态的唯一方式; 不用 `mv`, `cp` 或文件管理器代替.

```text
kanban init [project-path]
kanban rules
kanban list [--mobile] [backlog|todo|working|done|archived|trash]
kanban show <task-id>
kanban new [--large] <feature|bug|chore|research> <slug> <title...>
kanban move <task-id> <todo|working|done|archived|trash>
kanban pick [task-id]
kanban start [--agent codex|claude|grok] [--launcher tmux|foreground] [task-id]
kanban check
```

- `init` 幂等创建看板和 6 个状态目录. Git 项目只写本地 `.git/info/exclude`, 不改 `.gitignore`; 最后输出全局规则路径.
- `rules` 输出已安装的全局规则, 不要求当前目录存在看板.
- `list` 按状态分组, 组内按显示时间倒序; 同时或缺失时按任务 ID 倒序. 默认输出彩色表格并标出规模; `--mobile` 输出竖屏布局. `working` 显示开始时间, `done` 显示完成时间; 旧卡缺完成时间时用任务文档最后修改时间.
- `new` 在 `backlog/` 创建小任务; `--large` 创建含 `spec.md` 的大任务目录.
- `pick` 是 `backlog -> todo` 的便捷命令, 并执行 `todo` 完整性校验. 不给任务 ID 时只列候选.
- `move` 只执行「状态模型」允许的迁移, 并校验目标状态要求.
- `start` 只接受 `todo` 卡片. 它原子执行 `todo -> working`, 写负责人和开始时间, 再启动执行 Agent.
- `start` 的 Agent 默认取 Onevoke 配置 `kanban_agent`, 未完成 welcome 时回落到 Codex; `--agent` 只覆盖本次. 大任务用 Codex `gpt-5.6-sol/high` 或 Claude `opus/high`, 小任务用对应 `medium`; Grok 使用 CLI 默认模型和推理强度.
- `start` 默认使用 Agent 的免确认模式. launcher 默认取 Onevoke 配置, `--launcher` 只覆盖本次. `tmux` 只在当前 session 建 `kb-<任务标题>` window, 不创建 session; `foreground` 要求 stdin/stdout/stderr 都是 TTY, 并等待 Agent 退出. 两种模式的 cwd 都是项目根.
- `check` 列出全部无效入口并以非零退出. 其他命令忽略无关的无效入口, 只在目标任务违规时失败; 状态目录缺失或不可写时全部失败.
- 命令只做结构和机械校验. 授权, 依赖, 验收和终止理由由 Agent 按本文件判断.

## 状态模型

目录是状态唯一真源; 卡片正文不设 `status` 字段.

- `backlog/`: 已记录但尚未承诺执行.
- `todo/`: 用户已确认, 契约完整, 尚未领取.
- `working/`: 已领取, 正在实现, 验证, 审核, 验收或集成.
- `done/`: 已满足完成门禁的近期任务.
- `archived/`: 不占活跃看板的终态记录, 包括完成, 取消, 重复和不修复.
- `trash/`: 用户明确要求删除, 但尚未永久清理的入口; 不是任务状态.

```text
backlog -> todo -> working -> done -> archived
    |        |         |
    +--------+---------+-> archived

除 trash 外任意状态 -> trash, 仅限用户明确要求
```

- 进 `todo/` 前必须填完任务目标, 预期成果, 验收条件和不在本轮范围.
- 进 `done/` 前必须填写 `结果: completed`; 小任务还要完成总结, 大任务还要非空 `report.md`.
- 进 `archived/` 或 `trash/` 前按「终止与清理」填写结果和原因.

## 入口与文档

### 不变量

- 每个状态目录的直接子项是一个任务入口: 小任务为 `YYYYMMDD-short-slug-task.md`, 大任务为同名目录且必须含普通文件 `spec.md`.
- `short-slug` 只含小写 ASCII 字母, 数字和连字符. 去掉小任务扩展名后的入口名就是任务 ID.
- 任务 ID 在全看板唯一. 同 ID 不得跨状态重复, 也不得同时存在文件和目录形式.
- 迁移移动整个入口. 入口名创建后不改, 不复制后删, 不留平行副本.
- 卡片不得包含 token, 凭据, 敏感服务地址或不应留在本机的个人数据.
- 大任务目录内链接使用相对路径, 保证入口迁移后仍有效.

### 小任务模板

```markdown
# <任务标题>

- 类型: Feature | Bug | Chore | Research
- 创建时间: YYYY-MM-DD HH:MM
- 负责人:
- 开始时间:
- 完成时间:
- 任务分支:
- 结果:

## 任务目标

<改什么, 为什么改>

## 用户决策

<用户已确认的方向和取舍; 没有则写 N/A>

## 预期成果

<完成后可观察, 可验证的状态>

## 验收条件

- [ ] <条件>

## 威胁模型

<安全任务写资产, 可信主体和攻击者能力; 非安全任务写 N/A>

## 不在本轮范围

- <明确排除项及理由>

## 讨论与决策

<关键结论; 任务组卡片还要在开头记录任务组和前置任务>

## 实施与验证

<计划, 分支, commit, 验证命令, 结果, 环境缺口和阻塞>

## 完成总结

<实际成果, 偏差, 未处理问题和验收结论; 完成前留空>
```

### 大任务文档

- `spec.md` 必需, 使用小任务的元数据和契约章节: 任务目标, 用户决策, 预期成果, 验收条件, 威胁模型, 不在本轮范围, 讨论与决策.
- `plan.md` 按需创建, 记录实施步骤, 影响模块, 验证, 发布和回滚计划; 不得修改 `spec.md` 的契约.
- `report.md` 完成时创建, 记录实际改动, 最终 commit, 验证, 偏差, 未处理问题, 风险和验收结论; 不建空占位.
- `spec.md` 中的负责人, 开始时间, 完成时间, 任务分支和结果与小任务相同.

### 契约与记录

- 负责人, 开始时间和任务分支在领取后填写; 无代码分支写 `N/A`. 完成时间由命令迁入 `done/` 时填写.
- 结果只在进入 `done/`, `archived/` 或 `trash/` 前填写.
- 卡片进入 `todo/` 后, 任务目标, 用户决策, 预期成果, 验收条件, 不在本轮范围以及任务组关系冻结. 修改任何一项都要先取得用户明确决策.
- 实施期只追加关键决策, 实际验证, 环境缺口, commit, 阻塞和下一步, 不复制会话流水.
- 稳定的架构, API 和长期规则仍要写入仓库文档或项目规则, 不能只留在卡片里.

## 任务规模与任务组

- 小任务是单文件卡片. 大任务是需要独立 spec, 阶段计划和完整报告的单张卡片; 行数多不构成大任务.
- 同目标, 同负责人, 同验收和同生命周期的工作保留在一张卡内.
- 能独立领取, 验收或终止的工作必须拆卡. 一个总体目标含多名负责人或多条独立交付链路时, 建任务组, 不建包办全部实现的总卡.
- 拆分应减少依赖以提高并行度, 但不得制造职责重叠. 必须修改同一资源且不能安全隔离的卡片要建立依赖并串行执行.
- 新卡默认是小任务. 小任务变复杂时, 仅 `backlog/` 的当前编辑者或 `working/` 的负责人可以升级: 建同 ID 目录, 原内容转入 `spec.md`, 按需建 `plan.md`, 不保留原文件. `todo/` 中禁止改变形态.

任务组不是入口或状态, 只是一组独立卡片的关系. 每张组内卡片在 `讨论与决策` 开头各记录一次:

```text
任务组: YYYYMMDD-short-slug-group
前置任务: N/A
```

- 任务组 ID 在看板内唯一, 格式为 `YYYYMMDD-short-slug-group`. 所有组内卡片使用同一 ID.
- `前置任务` 是同组任务 ID 的逗号分隔列表; 无依赖写 `N/A`. 依赖只在前置卡进入 `done/` 后满足; `archived/` 和 `trash/` 不满足依赖.
- 建组时一次性列全卡片和依赖图, 确认无缺失引用, 循环依赖, 职责重叠或无法独立验收的卡片. 任务组关系在进 `todo/` 前填定.

## 创建与确认

收到 Bug 或功能开发需求时, 先完成需求分析和实施计划, 再一次性让用户选择:

```text
1. 确认计划并走看板 (建卡并启动)
2. 确认计划, 不走看板, 在本会话直接做
3. 调整计划
```

- 选 1 同时确认计划, 开发和看板流程, 不再重复确认开工. 单卡依次执行 `new`, 填卡, `pick`, `start`.
- 任务组的选 1 确认整组卡片和依赖. 一次性创建并填完全部卡片, `pick` 进 `todo/`, 再由编排 Agent 启动就绪卡; 不逐卡重复确认开工.
- 选 2 直接按项目规则实施, 不建卡. 选 3 继续调整计划, 不提前建卡或启动.
- 已由 `kanban start` 拉起, 已指定现有卡片, 纯问答, 只读排查, 纯文档或配置微调, 发布部署和合入操作, 不提供以上选项.
- `kanban new` 只创建模板. 执行它的 Agent 必须立即用当前会话已确认的内容填完契约, 不留 `<填写>`.
- 新卡先在 `backlog/`; 只有用户确认开发或用户明确授权的协调 Agent 才能移入 `todo/`. Agent 的建议不得冒充用户决策.

## 领取, 启动与协调

- 未指定任务且 `todo/` 有多张卡时, 列候选让用户选择; 任务组按已确认依赖排序, 不再逐卡询问.
- 开工条件不足时只报告缺口, 不领取, 不自动退回 `backlog/`.
- 动代码前必须先取得 `working/` 中的唯一入口. 两种领取方式互斥:

```sh
# 委派给新执行 Agent: start 原子领取并启动
kanban start [--agent codex|claude|grok] [--launcher tmux|foreground] <task-id>

# 当前 Agent 自己执行: 只迁移, 随后手工填写负责人和开始时间
kanban move <task-id> working
```

- 不得先 `move ... working` 再 `start`; `start` 只接受 `todo` 卡. 只有原子迁移成功者取得任务, 失败后立刻重查, 不建替代卡片.
- `start` 在启动前检查 Agent, launcher 和 TTY. 前置检查失败不领取; 创建进程或 tmux window 失败时恢复文档并迁回 `todo/`. 进程创建成功后即算启动成功, 后续退出不自动回滚.
- `start` 的初始 prompt 只传任务 ID 和固定要求. 执行 Agent 先读本规则, 卡片和项目规则, 再准备工作区并填写任务分支.
- 领取后只有执行负责人可修改或迁移 `working/` 入口. 协调 Agent和编排 Agent只能读取和督办; 明确交接后由新负责人接管, 不得并发写.
- 启动者在任务完成或明确交接前负责协调. tmux 模式定期查看卡片和执行进程; foreground 模式在 Agent 退出后检查结果. `start` 成功不代表协调职责结束.
- 同文件系统上的入口迁移是领取原语, 不增加 lock 服务, 数据库或 ID 分配器.

## 任务组编排

- 用户要求启动任务组后, 启动者转为编排 Agent. 它负责校验依赖, 通过 `kanban start` 委派就绪卡, 巡检, 协调恢复和确认组级结果, 不承担组内实现, 除非用户明确变更负责人.
- 编排前读取全组卡片, 核对 ID, 依赖图, 契约和修改范围. 有缺失引用, 环或无法隔离的冲突时不启动受影响卡片.
- 任务组必须使用 tmux launcher, 使编排会话和执行 Agent 可同时持续运行. 每张卡都显式用 `kanban start --launcher tmux <task-id>` 启动, 不依赖机器默认值. tmux 不可用时报告阻塞, 不以 foreground 启动任务组.
- 将已确认的 `backlog` 卡片移入 `todo/`; 已处于后续状态的卡片保持原状. 首轮启动无前置任务的 `todo` 卡, 以后仅启动全部前置卡都在 `done/` 的卡片. 同时就绪且无资源冲突的卡片并行启动.
- 编排会话持续到任务组成功或用户明确终止. 从首张卡启动起, 相邻两次巡检不得超过 30 分钟; 收到任务完成, Agent 消息或用户输入时立即处理, 不等下一周期.
- 每轮运行 `kanban check`, 查看全组状态, `working/` 卡的执行进程, 阻塞和完成记录, 然后立即启动新解锁的卡片. 进程存活不等于任务正常, 暂无新提交也不等于失败.
- 执行 Agent 异常退出时先核实卡片和 worktree. 原会话可恢复则恢复; 否则请求用户决定交接, 改契约或终止. `working` 卡不得再次调用 `kanban start`, 未受影响的链路继续推进.
- 全部组内卡片进入 `done/` 才算任务组成功. 任一卡进入 `archived/` 或 `trash/` 都不算成功; 编排 Agent 必须等待用户修改组契约或明确终止整个任务组.
- 编排结束时汇总执行顺序, 并行情况, 组级结果和遗留项. 另列"未处理问题", 按卡片逐项汇总审核未处理项, 验证缺口, 接受的风险和遗留问题; 没有写"无". 每项写任务 ID, 来源或类别, 档位, 问题, 影响和未处理理由; 安全审核超时项标记"超时忽略". 成功时单卡完成报告仍照常发送; 终止时列出未完成卡片和终止决策.

## 执行与完成

- `working/` 中按项目规则完成工作区准备, 实现, 验证, 提交, push, 审核, 验收, 集成和清理. 小任务写 `实施与验证`; 大任务按 `plan.md` 执行.
- 暂时失败或被阻塞时保留 `working/`, 写明阻塞和解除条件, 不自动归档.
- 安全审核的决策超时完全按 `~/.agents/REVIEW-RULES.md` 执行. 产生的未处理项写入小任务的 `实施与验证` 或大任务的 `plan.md`, 并带入完成总结或 `report.md`; 看板规则不另行定义审核门槛.
- 默认完成顺序如下. "验收请求"是集成前报告, 不是下节的最终完成报告:

```text
实现与验证 -> 必要审核 -> 向用户请求验收 -> 用户确认
-> 集成与清理 -> 写完成记录 -> move done -> kanban check -> 最终完成报告
```

- 合回时机取 `~/.agents/ONEVOKE-AGENTS.md`「看板任务完成」. 默认在实现, 验证和审核后先报告并等待用户确认; 未确认前不集成, 不清理, 卡片留在 `working/`. 安全审核的 15 分钟超时不适用于验收或集成确认.
- 只有实现完成, 验证结果已记录, 必要审核已完成, 用户验收已取得, 代码已按项目规则集成和清理后, 才能进入 `done/`. 非代码任务将不适用项记为 `N/A`.
- 进 `done/` 前, 在小任务填写完成总结, 或在大任务创建 `report.md`; 同时把 `结果` 填为 `completed`. 然后执行 `kanban move <task-id> done` 和 `kanban check`.

## 完成报告

- 卡片进入 `done/` 后, 执行 Agent 按下列模板汇报一次. 卡片未进 `done/`, 或代码任务尚未集成, 不发送最终完成报告.
- 小任务完成总结或大任务 `report.md` 先记录同一批事实; 报告只是汇总. 字段和章节不得省略, 无内容写 `无` 或 `N/A`.
- 验证只写实际结果; 失败, 未执行和环境阻塞不得写成通过. 最终提交使用完整 40 位 SHA.
- 审核未处理项逐项写来源角色, 档位, 问题, 影响和理由. 安全审核超时项还要写状态, 发送时间和超时时间, 不得写成 `PASS`, 用户确认或接受的风险.
- 剩余问题数包含审核未处理项, 验证缺口, 接受的风险, 遗留问题和后续任务; 同一根因只计一次, 已修问题和单纯计划偏差不计.

```markdown
# 看板任务完成报告

- 任务卡: [<task-id>](<done 下任务入口绝对路径>)
- 任务标题: <标题>
- 任务类型: <Feature | Bug | Chore | Research>
- 执行 Agent: <codex | claude | grok>
- 结果: `completed`
- 完成时间: <YYYY-MM-DD HH:MM>
- 任务分支: <`<任务分支>` | N/A>
- 集成分支: <`origin/develop` | `develop` | N/A>
- 最终提交: <`<完整 40 位 SHA>` | N/A>
- 看板状态: `done`

## 交付结果

- 用户结果: <用户最终能观察到的行为或成果>
```

## 终止与清理

- 用户明确取消, 判定重复, 决定不修或接受替代方向后, 可将 `backlog/`, `todo/` 或 `working/` 卡片直接移入 `archived/`. 实现困难, 验证失败或暂时阻塞不构成终止授权.
- 从活跃状态直接归档只能填写 `cancelled`, `duplicate` 或 `wontfix`, 并写明原因; `duplicate` 还要指向替代卡片. `completed` 只用于 `done -> archived`, 不得绕过完成门禁.
- `done/` 保留近期完成项, 用户确认无需展示后再归档.
- 只有用户明确要求删除具体卡片时才能移入 `trash/`. 迁移前填写 `结果: trashed`, 原因和时间. 不自动清空或永久删除 `trash/`; 永久删除需逐项授权.

## 异常恢复

- `working/` 卡片中断, 负责人为空或长期无进展时, 协调 Agent 可核实现场并恢复原会话; 其他 Agent 不得自行接管, 迁移或归档. 无法恢复时由用户决定交接或终止.
- 执行进程启动后退出, 卡片保留在 `working/`; 不自动退回 `todo/`, 不再次调用 `kanban start`.
- 出现重复 ID, 跨状态副本, 文件与目录同 ID, 大任务缺 `spec.md`, 目标冲突, 状态目录缺失或不可写时, 停止受影响操作并保留现场. 不通过删除, 改名或移动来绕过报错.
- 看板没有 Git 历史. 误删先检查 `trash/` 和本机备份, 不伪造恢复内容.
