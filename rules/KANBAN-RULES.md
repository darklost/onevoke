# 全局文件看板规则

## 适用范围与优先级

- 本文件适用于全局 `kanban` 命令管理的所有看板.
- 当前用户指令和目标项目规则优先于本文件. 代码实现仍须遵守目标项目的 `AGENTS.md` 或等价规则文件.
- 看板卡片是任务上下文, 不能覆盖仓库规则, 安全门禁或用户已明确的决策.
- Agent 操作看板时, 先通过 `kanban rules` 读取本文件, 再读取用户指定的卡片.

## 存储与定位

- `kanban/` 是本机共享目录, 不进入所属项目的 Git.
- 看板唯一实例位于主 worktree 根目录. 不在任务 worktree 中创建副本, 镜像或符号链接.
- Agent 在任意 worktree 中使用以下方式定位看板, 不硬编码本机绝对路径:

```sh
MAIN_WORKTREE="$(git worktree list --porcelain | sed -n '1s/^worktree //p')"
KANBAN_DIR="$MAIN_WORKTREE/kanban"
```

- 此看板只在共享同一主机和文件系统的 Agent 之间共享. 不假设远程 Agent 可见.
- 看板操作不需要任务分支, worktree, 提交, push 或代码审核. 卡片对应的代码任务仍完整执行目标项目流程.
- 不得对 `kanban/` 执行 `git add`, 不得强制加入 Git, 不得修改项目 `.gitignore` 来传播本机看板.

## 操作命令

- `kanban` 是创建, 查询, 迁移, 启动和检查任务入口的唯一支持命令. Agent 不直接用 `mv`, `cp` 或文件管理器迁移状态.
- 命令位于全局 `~/.local/bin/kanban`, 适用于采用相同目录约定的所有本机项目.
- 规则文件位于全局 `~/.agents/KANBAN-RULES.md`, 由 `kanban rules` 读取.
- 命令优先读取 `KANBAN_DIR`; 未设置时定位当前 Git 仓库主 worktree 的 `kanban/`, 再从当前目录向上查找 `kanban/`.
- `KANBAN_DIR` 仅供测试, 非 Git 项目或显式覆盖看板根目录; 正常 Git 项目不设置.

```text
kanban init [project-path]
kanban rules
kanban list [backlog|todo|working|done|archived|trash]
kanban show <task-id>
kanban new [--large] <feature|bug|chore|research> <slug> <title...>
kanban move <task-id> <todo|working|done|archived|trash>
kanban start [--agent codex|claude] [task-id]
kanban check
```

- `init` 幂等创建 `kanban/` 和 6 个状态目录. Git 项目同时把对应路径加入本地 `.git/info/exclude`, 不修改项目 `.gitignore`; 命令输出全局规则路径.
- `rules` 直接输出全局规则, 不要求当前目录存在看板.
- `new` 默认在 `backlog/` 创建小任务; `--large` 创建含 `spec.md` 的大任务目录.
- `move` 只允许本文件定义的正向迁移, 并校验目标不存在及迁移后状态.
- `start` 默认启动 `codex`; 可用 `--agent claude` 改为 Claude. 指定任务时只接受 `todo` 卡片; 未指定时列出 `todo` 卡片并要求用户按编号选择.
- `start` 只在当前 tmux session 新建并切换 window, 不创建 session. 新 window 的 cwd 是看板所属项目根目录, 名称为 `kb-<slug>`.
- 移入 `todo/` 前, 命令校验任务目标, 预期成果, 验收条件和不在本轮范围已填写.
- 移入 `done/` 前, 命令校验 `结果: completed`; 小任务还须完成 `完成总结`, 大任务还须完成 `report.md`.
- 移入 `archived/` 或 `trash/` 前, 先按对应规则填写 `结果` 和原因.
- `check` 列出全部无效入口并以非零状态退出. 其他命令忽略无效入口, 在 stderr 提示其数量, 只在被操作的任务本身违规时失败.
- 命令只执行结构及可机械验证的检查. 用户授权, 业务判断, 验收和归档理由仍由 Agent 按本文件确认.

## 目录状态

目录是卡片状态的唯一真源. 卡片正文不得再维护 `status` 字段.

- `backlog/`: 新需求, Bug, 想法和待讨论问题. 尚未承诺开发.
- `todo/`: 已确认开发且满足开工条件, 尚未领取.
- `working/`: 已被一个 Agent 或用户领取, 正在实现, 验证或等待验收.
- `done/`: 已完成实现, 验证, 用户验收和必要集成的近期任务.
- `archived/`: 不再占用活跃看板的终态记录, 包括已完成, 取消, 重复和不修复.
- `trash/`: 用户明确要求删除但暂未永久清理的文档. 它不是任务状态.

允许的正常迁移:

```text
backlog -> todo -> working -> done -> archived
    |        |         |
    +--------+---------+-> archived

任意目录 -> trash 仅限用户明确要求
```

## 任务入口不变量

- 状态目录下的每个直接子项是一个任务入口. 任务入口可为小任务 Markdown 文件或大任务目录.
- 小任务入口命名为 `YYYYMMDD-short-slug-task.md`.
- 大任务入口命名为 `YYYYMMDD-short-slug-task/`, 且必须包含 `spec.md`.
- `short-slug` 使用小写 ASCII 字母, 数字和连字符, 不使用空格.
- 任务 ID 是去掉小任务 `.md` 后的入口名. 同一任务 ID 的文件和目录形式不得同时存在.
- 一个任务入口同时只能存在于一个状态目录. 状态迁移移动整个入口, 不逐个移动目录内文档.
- 入口名创建后保持不变. 不复制后删除, 不保留平行副本.
- 任务 ID 必须在整个看板内唯一. 发现同 ID, 同名或重复任务时停止操作并报告用户.
- 卡片不得包含 token, 凭据, 敏感服务地址或不应留在本机文档中的个人数据.

## 文档结构

```text
todo/
|-- 20260801-small-fix-task.md
`-- 20260801-large-feature-task/
    |-- spec.md
    |-- plan.md
    `-- report.md
```

- 小任务以单个 `*-task.md` 承载需求契约, 简单计划, 实施验证和完成总结.
- 大任务以 `*-task/` 承载多个语义独立文档. 不因单纯行数增加而拆分.
- 同一目标, 负责人, 验收和生命周期的内容留在一个任务入口.
- 可独立领取, 验收或终止的工作必须拆成多个任务入口, 不写成同一目录中的阶段文档.
- 目录内链接使用相对路径, 保证任务入口移动后仍有效.

### 小任务模板

```markdown
# <任务标题>

- 类型: Feature | Bug | Chore | Research
- 创建时间: YYYY-MM-DD HH:MM
- 负责人:
- 开始时间:
- 任务分支:
- 结果:

## 任务目标

<改什么, 为什么改>

## 用户决策

<用户已确认的方向和取舍; 没有则写 N/A>

## 预期成果

<完成后可观察, 可验证的状态>

## 验收条件

- [ ] <条件>

## 威胁模型

<安全任务写资产, 可信主体和攻击者能力; 非安全任务写 N/A>

## 不在本轮范围

- <明确排除项及理由>

## 讨论与决策

<按时间追加关键结论, 不写无意义流水>

## 实施与验证

<计划, 分支, commit, 验证命令, 结果和环境缺口>

## 完成总结

<实际成果, 偏差, 遗留项和验收结论; 完成前留空>
```

### 大任务文档

- `spec.md` 是必需入口文档. 使用小任务模板中的元数据和以下契约段落: `任务目标`, `用户决策`, `预期成果`, `验收条件`, `威胁模型`, `不在本轮范围`, `讨论与决策`.
- `plan.md` 按需创建. 记录实施步骤, 影响模块, 验证方案, 发布或回滚要求. 它不得改变 `spec.md` 的任务契约.
- `report.md` 在任务完成时创建. 记录实际改动, 最终 commit, 实际验证, 计划偏差, 遗留项, 接受的风险和验收结论.
- 大任务进入 `done/` 前必须存在 `report.md`. 未完成时不创建空报告占位.
- `spec.md` 中的 `负责人`, `开始时间`, `任务分支`, `结果` 与小任务同义.

### 选择与升级

- 单目标, 单负责人, 实施直接且验证简单时使用小任务单文件.
- 需要独立 spec, 分阶段计划或完整完成报告时使用大任务目录.
- 新任务默认使用小任务单文件; 已明确满足大任务条件时可直接创建目录.
- 小任务变复杂时, 在 `backlog/` 由当前编辑者升级, 或在 `working/` 由负责人升级. `todo/` 中不得改变入口形态.
- 升级时创建同 ID 目录, 将原文件内容移入 `spec.md`, 按需创建 `plan.md`; 完成转换后不得保留原 `*-task.md`.

- `负责人`, `开始时间`, `任务分支` 在领取后填写. 无代码分支时写 N/A.
- `结果` 只在进入 `done/`, `archived/` 或 `trash/` 时填写.
- 进入 `todo/` 后, `任务目标`, `用户决策`, `预期成果`, `验收条件` 和 `不在本轮范围` 构成任务契约. Agent 不得静默改写; 需要改变时先取得用户明确决策.
- 稳定的架构, API 或长期规则仍须沉淀到仓库文档或对应 `AGENTS.md`, 不只留在卡片中.

## 创建与确认

- 新需求, Bug 或想法默认在 `backlog/` 创建任务入口.
- `backlog/` 中允许继续补充调查, 方案, 用户决策和验收条件.
- 只有用户明确确认开发, 或用户明确授权的协调 Agent 才能将卡片移到 `todo/`.
- 移入 `todo/` 前必须至少明确任务目标, 预期成果, 验收条件和不在本轮范围. 缺失时继续留在 `backlog/`.
- 大任务移入 `todo/` 前必须确认 `spec.md` 存在且可读. `plan.md` 可在领取后补充.
- Agent 不得把自己的建议当作用户决策写入卡片.

## 领取与并发

- 用户应指定要开始的任务入口. 若 `todo/` 中有多个且用户未指定, Agent 先列出候选并请用户选择, 不自行猜测优先级.
- Agent 可先只读检查小任务文件或大任务 `spec.md`. 不满足开工条件时报告缺口, 不领取, 不自动退回 `backlog/`.
- 开始任何代码修改前, Agent 必须先将整个任务入口从 `todo/` 移到 `working/`.
- 领取必须通过命令执行:

```sh
kanban move <task-id> working
kanban start [--agent codex|claude] [task-id]
```

- 只有命令迁移成功者获得任务. 失败, 源文件消失或目标已存在时, 立即停止领取并重新检查; 不创建替代卡片.
- 成功领取后立即在小任务文件或大任务 `spec.md` 中填写负责人和开始时间, 再按目标项目规则准备工作区, 随后填写任务分支; 无分支时写 N/A.
- `start` 在启动 Agent 前原子迁移卡片并填写负责人和开始时间. tmux 或 Agent binary 前置校验失败时不领取; `tmux new-window` 同步失败时恢复原文并移回 `todo`.
- `start` 传给 Agent 的初始 prompt 只含已校验任务 ID 和固定执行要求, 不把卡片正文拼入 shell command. Agent 启动后先读取本规则和卡片, 再补充任务分支并执行任务.
- tmux window 创建成功即视为启动成功. Agent 随后退出、认证失败或执行中断时, 卡片继续留在 `working/`, 按异常恢复规则处理, 不自动退回 `todo/`.
- 同一文件系统中的移动是领取原语. 初始方案不增加 lock 服务, 守护进程, 数据库或任务 ID 分配器.
- 领取后只有负责人可修改任务入口内文档. 其他 Agent 可读取, 但不得并发写入或移动.

## 开发, 验证与验收

- 任务进入 `working/` 后, 代码修改按目标项目规则执行, 包括适用的工作区, 验证, 提交, push, 审核, 验收, 集成和清理.
- 小任务在原文件的 `实施与验证` 和 `完成总结` 中记录结果. 大任务按 `plan.md` 实施, 完成时写 `report.md`.
- 实施期间只记录关键决策, 实际验证结果, 环境缺口, commit 和下一步. 不把完整会话流水复制到任务文档.
- 代码完成但尚未验收时, 卡片继续留在 `working/`; 不提前移入 `done/`.
- Bug 修复必须遵守目标项目的验收门禁. 未获所需确认时不得以 "代码已完成" 为由标记 `done`.
- 任务被阻塞时继续留在 `working/`, 写明阻塞条件和解除条件. 不因暂时失败自动归档.
- 只有实现完成, 直接验证通过, 必要审核通过, 用户验收完成且代码已按规则集成后, 才能移入 `done/`.
- 移入 `done/` 前在小任务文件或大任务 `spec.md` 中填写 `结果: completed`, 并完成总结或 `report.md`.

## 终止与归档

- 已取消, 重复, 明确不修复或方向被替代的卡片可从 `backlog/`, `todo/` 或 `working/` 直接移入 `archived/`.
- 终止开发必须由用户明确决定. Agent 不得仅因实现困难, 验证失败或暂时阻塞自行终止.
- 归档前填写以下一种结果: `completed`, `cancelled`, `duplicate` 或 `wontfix`.
- 非 `completed` 结果必须记录原因; `duplicate` 还须指向替代卡片.
- `done/` 保存近期已验收任务. 用户认为无需继续展示时再移入 `archived/`, 不设自动期限.
- 归档不是永久保留义务. 无决策价值且长期知识已沉淀到仓库的中间卡片, 可由用户决定移入 `trash/`.

## Trash 与清理

- 只有用户明确要求删除某张卡片时, 才能将其移入 `trash/`.
- 移入前在小任务文件或大任务 `spec.md` 中填写 `结果: trashed`, 并记录删除原因和时间.
- Agent 不得自动清空 `trash/`, 不得设置定时清理, 不得永久删除其中内容.
- 永久清理由用户执行或逐项明确授权. 授权必须指出具体文件, 不能笼统解释为清空全部.

## 异常恢复

- `working/` 中负责人为空, 任务中断或长期无进展时, 其他 Agent 不得自动接管, 移回或归档; 先报告用户决定.
- Agent 在领取后异常退出, 卡片仍保持 `working/`. 后续 Agent 根据用户决定继续, 重新指派或归档.
- 发现同一任务 ID 同时存在于多个目录, 文件和目录形式同时存在, 大任务缺少 `spec.md`, 目标入口冲突, 状态目录缺失或无法写入时, 停止受影响操作并保留现场.
- 受影响范围以任务为单位: 违规任务的 `show`, `move`, `start` 一律失败并给出原因, 未受影响的任务照常操作. 状态目录缺失或无法写入时全部命令失败. Agent 不得为绕过报错自行删除, 改名或移动无效入口, 先报告用户.
- 看板不进 Git, 不具备 Git 历史恢复能力. 误删时先检查 `trash/` 和本机备份, 不伪造恢复内容.
